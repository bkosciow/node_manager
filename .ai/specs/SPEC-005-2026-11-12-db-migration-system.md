# SPEC-005 — Database Migration System (Alembic)

## Overview

Schema changes today happen by writing raw `ALTER TABLE` SQL against the
live database by hand (the pending `devices.last_seen_at/last_updated_at`
ALTER from quick-spec 002 is the current example). `init_db()` /
`Base.metadata.create_all()` only ever creates missing *tables* — it can't
add columns, drop columns, or rename anything — so every real schema
change is an untracked, unrepeatable SQL session.

This spec replaces that with a versioned migration system:

1. **Alembic** as the migration engine — revision graph in
   `migrations/versions/`, autogenerate diffs from the SQLAlchemy models
   (no hand-written DDL), programmatic `upgrade head` at app startup.
2. **App-startup run point** — every entrypoint (`rest_server`,
   `device_scaner`, `repo_scanner`) runs `alembic upgrade head` in-process
   before touching the DB. Idempotent no-op when the schema is current.
3. **Dev DB reset to a clean baseline** — the dev database
   (`node_manager_dev`, compose `db` service) is dropped and recreated,
   then the **baseline migration** (revision `0001`, autogenerated against
   the empty schema = the entire current model set, *including* the
   `last_seen_at`/`last_updated_at` columns) is applied. No manual ALTER,
   no backfill — the quick-spec 002 migration step is superseded.
4. **`create_all` retired from app code paths** — `init_db()` is removed;
   tests keep their own independent SQLite `create_all` (they must stay
   independent of migrations for speed).

**Not in scope:** prod reset (documented in the ops runbook below,
executed with the user's explicit go-ahead at deploy time), any
down-migration support (Alembic downgrades exist but are not a workflow
here — forward-only), concurrency locking beyond what Alembic provides.

**What already exists (do not rebuild):**
- `app/db/session.py` — `engine` + `SessionLocal` + `get_db()` stay as-is
  (only `init_db()` is removed).
- `settings.database_url` (env `DATABASE_URL`) — single source of the DB
  URL for both the app and the migrations (config-settings standard).
- The models barrel `app/models/__init__.py` — gives `Base.metadata` all
  tables; that is what Alembic autogenerate diffs against.
- Docker/Compose layout — no compose changes needed: the app containers
  already start the entrypoints that will now run migrations.
- `make dev-repo-scanner` exists in the `Makefile` (dev-venv wrapper
  around `repo_scanner.py`) — Story 3 / runbook step 5 rely on it;
  confirmed present before relying on it.

## User Stories

### Story 1 — Happy path: adding a model column, no SQL ever

> **Persona**: Operator (project owner) extending `Device` with a new
> column in a dev session. Comfortable with git/pytest, wants to ship
> without opening a MySQL shell.

1. Edit `app/models/device.py` (add `battery_level` column).
   ```
   battery_level: Mapped[int] = mapped_column(Integer, default=0)
   ```
   **Behind the scenes**: models are the single source of truth for
   `Base.metadata`; nothing touches the DB yet.
2. `make autogenerate` → runs `alembic revision --autogenerate` against the
   dev DB; Alembic diffs `Base.metadata` vs the `alembic_version`-known
   state and writes `migrations/versions/00NN_add_battery_level.py`
   containing `op.add_column(...)`.
   **Change vs. current state**: today this step is *a human writing and
   running `ALTER TABLE devices ADD COLUMN …` on the live DB* —
   untracked, unrepeatable, and wrong-by-default if missed on prod.
3. Review the generated revision file, commit it with the model change.
4. `make dev` (or `docker compose up -d api`) — the api container's
   `startup()` runs `run_migrations()` → `upgrade head` applies the
   pending revision before the first request. Same for scanner/repo_scanner
   containers on their next start.
   **Behind the scenes**: `run_migrations()` (new `app/db/migrate.py`)
   builds an Alembic `Config` anchored at the repo root, overrides
   `sqlalchemy.url` with `settings.database_url`, and calls
   `command.upgrade(cfg, "head")`. Current schema → zero revisions run,
   sub-second no-op.

### Story 2 — Alternative flow: brand-new database, zero manual steps

> **Persona**: Operator provisioning a fresh machine (or this spec's dev
> reset). No MySQL experience required beyond `docker compose up`.

1. Fresh MySQL (compose `db` service, `MYSQL_DATABASE=node_manager_dev`).
2. `docker compose up -d api` — **Change vs. current state**: today a new
   DB is bootstrapped by `init_db()` = `create_all()` which *only* creates
   missing tables and cannot evolve an existing one; a fresh DB "works"
   only while the models haven't changed shape. After this spec, the api
   container's startup runs the full revision graph (baseline first) and
   the schema is exactly what the committed migrations describe.
3. `curl localhost:9092/health` → `{"status": "ok"}`; `devices` table
   exists with all current columns.

**Comparison — schema bootstrap mechanism:**

| | Today | After SPEC-005 |
|---|---|---|
| New DB | `create_all()` from `Base.metadata` | baseline + pending revisions via `upgrade head` |
| Changed DB | hand-written raw SQL (error-prone, untracked) | `make autogenerate` → committed revision → applied at startup |
| Repeatable | no | yes (revision files in git) |
| Diffs models vs DB | no | yes (autogenerate) |

### Story 3 — Edge case: dev DB reset (this spec's one-time migration)

> **Persona**: Operator executing the one-time dev reset. Knows the dev DB
> holds only disposable state (discovered devices, repo→node assignments,
> ephemeral upgrade sessions).

1. Confirm dev api/scanner containers are stopped (the dev `db` service
   stays up).
2. First-time only — generate and commit the baseline (the one-time
   chicken-and-egg ordering, §Architecture “One-time baseline
   procedure”):
   - `docker compose exec db mysql -uroot -ppostgres -e
     "DROP DATABASE IF EXISTS node_manager_dev; CREATE DATABASE
     node_manager_dev"` (dev compose `db` service; root password is
     `postgres` per `MYSQL_ROOT_PASSWORD` in `docker-compose.yml`) —
     db-level grants survive drop/create of the same database name; the
     app user `node_manager` keeps working.
   - `.venv/bin/alembic revision --autogenerate -m "baseline"` against
     the now-empty schema → review + `git commit`
     `migrations/versions/0001_baseline.py`.
   - `.venv/bin/alembic upgrade head` → baseline revision creates all
     tables (this is also the moment the quick-spec 002 columns land —
     no separate ALTER/backfill).
   **Change vs. current state**: today the dev DB accumulates ad-hoc
   state and schema drift (the pending ALTER would have been applied by
   hand, forever out of sync with git).
   **Repeat resets** (after the baseline is committed): just
   `make reset-dev-db` (guarded drop/create + `upgrade head`).
3. `docker compose up -d api scanner` → both containers run
   `upgrade head` (no-op now), `/health` OK.
4. Manual follow-up (accepted cost, stated by the owner): re-assign
   repositories to nodes (`POST /api/repos/{id}/nodes`), re-scan repos
   (`make dev-repo-scanner`); devices re-discover themselves via the UDP
   scanner within one ping cycle.
5. **Prod (later, explicit approval only):** same drop/create + `upgrade
   head` run against the prod MySQL during the deploy window, then
   re-assign repos to nodes. Documented in the runbook below; *not
   executed by this spec's implementation*.

## Architecture

**New files:**

| File | Role |
|---|---|
| `alembic.ini` (repo root) | Alembic config: `script_location = migrations`, empty `sqlalchemy.url` (injected at runtime — see below). `prepend_sys_path = .` so CLI use from the repo root can import `app.*`. |
| `migrations/env.py` | `target_metadata = Base.metadata`; imports `app.models` (barrel) so autogenerate sees every table; URL resolution: explicit ini value → else `settings.database_url` (`.env` / env var); standard offline/online `run_migrations`. |
| `migrations/script.py.mako` | Standard revision template. |
| `migrations/versions/0001_baseline.py` | **Autogenerated** against the empty dev schema: creates all current tables (`devices`, `device_events`, `device_ignored_files`, `node_repositories`, `repositories`, `repository_files`, `node_updates`, `node_update_files`) incl. `devices.last_seen_at` / `last_updated_at`. |
| `app/db/migrate.py` | `run_migrations() -> None`: builds the Alembic `Config` from `<repo_root>/alembic.ini` (anchored via `Path(__file__).resolve().parents[2]`, so it works from any CWD incl. the Docker WORKDIR), sets `sqlalchemy.url` from `settings.database_url`, calls `command.upgrade(cfg, "head")`, logs the result. Repo root = parents of `app/db/migrate.py` → `node_manager/`. |

**Venv sync (once, after the requirements.txt change):**
`source .venv/bin/activate && pip install -r requirements.txt` — after this,
`.venv/bin/alembic` exists and every Make target above is actionable from
a fresh clone + this one sync step.

**`make reset-dev-db` — dev-only guard + procedure (Makefile reads `.env`):**

- `DATABASE_URL := $(shell sed -n 's/^DATABASE_URL=//p' .env)` — the target
  reads the URL from the repo `.env` (Make does not load `.env` itself;
  this mirrors what `Settings` sees at runtime).
- Guards (two distinct diagnostics, checked before anything is printed
  or run):
  - `$(DATABASE_URL)` empty (missing `.env` or no `DATABASE_URL=` line)
    → `$(error .env DATABASE_URL not found — create .env (see .env.example) first)`
  - `$(DATABASE_URL)` non-empty but not containing `node_manager_dev`
    → `$(error reset-dev-db is dev-only: DATABASE_URL must target node_manager_dev)`
- Procedure (each step printed before execution):
  1. `docker compose exec db mysql -uroot -ppostgres -e "DROP DATABASE IF EXISTS node_manager_dev; CREATE DATABASE node_manager_dev"`
     (dev compose `db` service, `MYSQL_ROOT_PASSWORD=postgres` per
     `docker-compose.yml`; db-level grants on the `node_manager` app user
     survive drop/create of the same database name).
  2. `.venv/bin/alembic upgrade head` — applies the committed baseline.
     If `migrations/versions/` is empty, the target errors with a hint to
     generate the baseline first (procedure below).

**Revision naming convention (pinned — resolves the `0001` vs hex-ID ambiguity):**
Alembic by default emits a *random hex* revision id and a hex-named file.
This project instead uses **sequential 4-digit revision ids**:

- The revision **id** and the **filename prefix** are the same 4-digit
  number (baseline = `0001`; each later revision is `NNNN` = previous + 1).
- The root `alembic.ini` cannot auto-increment filenames (its
  `file_template` only supports the `%(rev)s`, `%(slug)s`, `%(time)s`
  tokens), so the convention is enforced manually after each autogenerate:
  1. `alembic revision --autogenerate -m "<slug>"` → creates
     `migrations/versions/<hex>_<slug>.py`.
  2. `git mv` / rename it to `NNNN_<slug>.py` (NNNN = next sequential).
  3. Set the `revision = "NNNN"` string at the top of the file, and
     `down_revision = "NNNN-1"` (baseline: `down_revision = None`).
- A fresh session reading “revision 0001” / “00NN” in this spec always
  means *both* the id value and the file prefix.

**One-time baseline procedure (ordered; breaks the chicken-and-egg):**

```
0. make reset-dev-db step 1 only (drop/create the empty schema)
   — or: docker compose exec db mysql -uroot -ppostgres -e
          "DROP DATABASE IF EXISTS node_manager_dev; CREATE DATABASE node_manager_dev"
1. .venv/bin/alembic revision --autogenerate -m "baseline"
   (empty schema → full CREATE of every table; reviews cleanly as one file)
   then apply the naming convention above: rename to 0001_baseline.py,
   set revision = "0001", down_revision = None
2. review + git commit migrations/versions/0001_baseline.py
3. .venv/bin/alembic upgrade head   (= `make migrate`)
```

After step 2, `make reset-dev-db` works standalone (drop/create + step 3).

**Workflow rule (goes into the updated standards + AGENTS.md Commands):**
model change → `make autogenerate` → review + commit the revision →
applied automatically on next app/container start (or `make migrate`).
No raw DDL against dev/prod ever again; no SQL files under `upgrades/`
(repo_scanner data dir — the no-sql-migration-files rule, now structural).

**Standards targets (sync-standards phase):**
- New `.ai/standards/database/migrations.md` (+ `index.yml` entry):
  autogenerate workflow, `run_migrations()` at every entrypoint,
  no `create_all` in app code paths, baseline procedure,
  never-edit-applied-revisions rule, no SQL under `upgrades/`.
- Update `.ai/standards/cli/standalone-db-bootstrap.md`: scripts call
  `run_migrations()` instead of `Base.metadata.create_all`; the
  own-engine + one-session-per-run structure is unchanged.
- Replace the GUARDRAILS.md architectural decision "Schema = models,
  no migration tool" (which says never add Alembic without changing it)
  with the SPEC-005 decision: Alembic is the migration engine; model
  changes go through autogenerate; committed revisions apply at startup.

**Test strategy (suite stays migration-independent):**
- `tests/conftest.py` `client` fixture triggers FastAPI lifespan today
  (`with TestClient(app) as c`), which runs `startup()` → `init_db()` —
  a known quirk: that `create_all` runs against the *module engine*
  (`settings.database_url` = the dev MySQL), idempotently no-opping
  because the real tables exist. The test's own SQLite `create_all`
  (in the fixture) is what actually serves the tests.
- After this spec: the new conftest autouse fixture monkeypatches
  `app.rest_server.run_migrations` to a no-op **before** the TestClient
  context enters, so lifespan can never reach Alembic or the real DB.
  All `Base.metadata.create_all` calls in test files stay untouched.
- New unit test for `run_migrations()` itself, in **`tests/unit/test_migrate.py`**
  (new file): monkeypatch `settings.database_url` to a temp **SQLite**
  file URL, call `run_migrations()`, assert an `alembic_version` row +
  the baseline tables exist. If the committed baseline revision turns
  out to use MySQL-specific DDL that SQLite rejects, the test is
  `pytest.mark.skip(reason="baseline DDL is MySQL-specific")` and the
  SQLite assertion is dropped — decided at implementation, recorded in
  the changelog.

**Acceptance criteria ("done when"):**
1. `pytest tests/ -q` green + `flake8 app/ tests/ --count` = 0.
2. `alembic current` (dev venv) == `head`; `dev` DB `devices` table has
   `last_seen_at` / `last_updated_at` columns.
3. `docker compose up -d api scanner` → both containers healthy;
   `GET /api/devices` returns 200.
4. Restarting api with the schema already at head logs a no-op
   migration run (no revision applied).

**Concurrency note (accepted, documented):** api and scanner containers
can start simultaneously and both run `upgrade head`. Alembic checks the
`alembic_version` table between revision steps; for the single-revision
baseline the race window is negligible at this scale, and a losing process
simply no-ops. No `GET_LOCK` wrapper (YAGNI).

**Failure modes:**
- DB unreachable at startup → `run_migrations()` raises → app fails to
  start → container restart policy retries (identical to today's
  `init_db()` behavior — parity, not regression).
- Malformed/failed revision → logged, app does not serve; fix/forward-port
  the revision, restart. Never edit an already-applied revision file.

## Data Models

No model changes in this spec. Baseline revision encodes the current
model set verbatim, plus `alembic_version` (Alembic-managed:
`version_num VARCHAR(32) PRIMARY KEY`).

## API Contracts

No REST endpoint changes. New operator commands:

```
make migrate          # alembic upgrade head (dev venv)
make autogenerate     # alembic revision --autogenerate -m "<msg>" (MSG required)
make reset-dev-db     # dev-only: drop/create node_manager_dev + upgrade head
```

## Configuration

No new env vars. `DATABASE_URL` (existing, config-settings standard) is
the single URL source for app **and** migrations:
- Docker: compose injects `DATABASE_URL` → `settings.database_url` picks
  the env var (`.env` is not shipped in the image).
- Local dev: `Settings` reads `.env` in the repo root (CWD of the
  venv/CLI runs).
- `alembic.ini` intentionally carries **no** credentials — the URL is
  always injected from settings (env.py falls back to
  `settings.database_url` when the ini value is empty).

## Ops Runbook

### Dev reset (executed by this spec's implementation)

First-time (baseline not yet committed) — use the §Architecture
“one-time baseline procedure”: drop/create the empty schema,
`alembic revision --autogenerate -m "baseline"`, commit
`0001_baseline.py`, then `alembic upgrade head`.

```
# repeat resets, once the baseline revision is committed:
1. docker compose ps            # confirm api/scanner not running (db stays up)
2. make reset-dev-db           # guarded drop/create + `alembic upgrade head`
3. docker compose up -d api scanner   # (or `make dev` for venv dev)
4. curl -H "Authorization: Bearer $API_TOKEN" localhost:9092/api/devices
                                 # 200, empty list
5. manual: re-assign repos to nodes, `make dev-repo-scanner`
```

Dev DB credentials (for reference): compose `db` service root password
`postgres` (`MYSQL_ROOT_PASSWORD`); app user `node_manager` / `postgres`
(the `node_manager_dev` DB is on host port 3308 in dev).

### Prod deploy (later — explicit user approval required; see
no-auto-deploy-prod rule)

Decision: **DROP DATABASE + CREATE (fresh schema)** — the owner has
stated prod is still fresh and rebuildable (repo→node re-assignment is
a quick manual task). No in-place truncate/reset variant.

```
1. deploy window: stop api/scanner services
2. against prod MySQL (external; no db service in docker-compose.prod.yml):
   DROP DATABASE <node_manager schema>; CREATE DATABASE <node_manager schema>
3. deploy new image; api/scanner start → `upgrade head` applies baseline
4. re-assign repos to nodes; verify /api/devices + /health
```

## Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Integration tests (TestClient lifespan) accidentally run the new `run_migrations()` against the real DB | conftest autouse fixture monkeypatches `app.rest_server.run_migrations` to a no-op before the client context enters; suite stays SQLite-only (see §Architecture “Test strategy”) |
| Baseline revision generated from dev MySQL has MySQL-specific DDL that a SQLite unit test rejects | Tests don't run migrations in the suite (own `create_all`); the `run_migrations()` unit test targets SQLite only if DDL is dialect-safe, else marked skip-with-reason |
| `make reset-dev-db` pointed at the wrong DB | hard guard: target reads `DATABASE_URL` from `.env` and errors unless it contains `node_manager_dev`; prints the exact command before running |
| Two containers racing on `upgrade head` | documented, accepted (single-revision baseline; no-op after first apply) |
| Future autogenerate misses a change (e.g. a column added only in SQL) | that failure mode *is* what this spec eliminates — all changes go through models + autogenerate |
| `repo_scanner` keeps own-engine session semantics | only the `create_all` line is replaced; session structure untouched (standalone-db-bootstrap standard, updated via sync-standards) |
